# Independent investigation evolution scenarios

## Evidence and classification

- Evidence packet: `OTEL-INVESTIGATION-1`; baseline commit: `ed6e5038d82d67298c8a569ad67f955caadd5cc9`.
- Requirement inputs: `requirements.md`, `specs/telemetry-investigation/spec.md`, and `specs/telemetry-diagnostics/spec.md` in this change. Baseline facts come only from sources linked by that packet.
- The scenario author has no proposed model, interface, package plan, or design input. This document contains no implementation prescription or gate verdict.
- Layer follows the changing condition: user behavior and interpretation rules belong to conceptual/responsibility review; storage, integration, operation, and technology conditions belong to architecture/interface review.
- Confidence describes the evidence: **Observed** exists in baseline evidence; **Committed** is an accepted requirement; **Evidence-backed plausible** is supported by the packet without being scheduled; **Speculative** lacks supporting evidence and cannot require an extension point.

## Scenarios

| Scenario | Layer | Confidence | Change Source/Evidence | Requirement or External Condition That Changes |
| --- | --- | --- | --- | --- |
| S1. A user investigates the fourth or later failure episode, opens its precise span beyond the current page, switches investigation purpose, and returns to the originating conversation. | Conceptual/responsibility — user investigation | Committed | R1–R3; accepted scenarios “Target outside the visible page” and “More than three episodes.” Baseline [navigation](https://github.com/kotokumu/agentmetry/blob/main/web/src/app/navigation.ts) preserves selected agent and scroll and carries trace/span anchors. | The target changes from a visible trace-level entry to an exact activity elsewhere in the result. Conversation, selected agent, active filters, purpose, position, and evidence identity must survive the journey; all returned episodes remain accessible with their analysis coverage. |
| S2. A user narrows the conversation set to observed failures, minimum duration, model, and tool, then enters an invalid numeric condition. The model and tool matches occur in different activities, and the matching conversation is outside the loaded page. | Conceptual/responsibility — selection rules | Committed | R4; accepted scenarios “Filter matches outside the loaded page” and “Model and tool in different activities”; packet error case “Invalid filter.” | Query conditions become more selective without changing their conversation-level meaning. Conditions apply before pagination, results contain each conversation once, and unknown values do not become positive matches. Invalid input must leave the last applied query distinguishable from the attempted query. |
| S3. A user reuses a named relative-time investigation on a later day, replaces its conditions, and uses browser back/forward across different applied conditions. | Conceptual/responsibility — repeated investigation | Committed | R5; accepted scenario “Restore saved conditions”; packet edge case “relative saved time advancing.” | The clock and active named conditions change. A saved relative window describes conditions evaluated now, not a frozen execution set; replacement/deletion and URL/history restoration must preserve the distinction between saved and currently applied conditions. |
| S4. The selected baseline is changed to a conversation from another source with the same unqualified ID, an overlapping conversation, the current conversation itself, or a conversation with invalid time; a separate caller still requests the existing aggregate comparison. | Conceptual/responsibility — identity and comparison eligibility | Committed | R7/R8; packet source-qualified identity and edge cases; baseline [MCP comparison](https://github.com/kotokumu/agentmetry/blob/main/internal/transport/mcpserver/server.go) accepts one to ten explicit runs. | Normalized pair eligibility changes with source-qualified identity and time, while aggregate comparison retains its existing admissible requests. Rejection must identify the actual problem without substituting another baseline or restricting the older aggregate behavior. |
| S5. An eligible pair has complete retained-projection analysis, but one run has no outcome-known validations or no reported token numerator; another valid observation contains a reported zero. The pair is inspected through both clients. | Conceptual/responsibility — measurement meaning | Committed | R7/R8/R11; accepted scenario “Insufficient denominator”; packet edge cases “zero denominator” and “missing versus zero token usage.” | Available evidence changes independently of analysis completeness. The five diagnostics preserve their identities, units, numerators, denominators, availability reasons, and deltas across Web/MCP; absent evidence cannot become zero or proof of task achievement. |
| S6. Received content varies between a file reference, a tool-read body, an explicitly reported model input, a producer-redacted prompt, and a missing field with no redaction indicator. | Conceptual/responsibility — content interpretation | Observed | R9/R10; accepted content scenarios; [Codex content controls](https://github.com/kotokumu/agentmetry/blob/main/docs/source-telemetry/codex.md) distinguish prompt redaction and log/trace fields; [Claude content controls](https://github.com/kotokumu/agentmetry/blob/main/docs/source-telemetry/claude-code.md) document separately gated content. | Evidence strength and content availability vary by the received record and verified mapping. File names/read results cannot establish later model inclusion; redaction remains explicit, unknown causes remain unknown, and external files/services cannot fill missing bodies. |
| S7. The user changes to a narrow viewport or 200% browser zoom and performs selection, episode expansion, view switching, filter application, evidence reading, and return entirely by keyboard. | Conceptual/responsibility — interaction constraints | Committed | R3/R13; accepted scenarios “Narrow layout and live arrival” and “Keyboard investigation at enlarged text size.” | Available screen space and input method change. The selected activity, body, return action, focus destination, and failure/missing states must remain identifiable and reachable without color alone. |
| S8. A trace grows to 1200 projected activities while only one detail page is loaded; the user zooms a long interval, applies type/error filters, and selects an activity outside the visible range. | Architecture/interface — data volume and bounded reads | Committed | R6/R11 and the long-trace non-functional constraint; [baseline trace query](https://github.com/kotokumu/agentmetry/blob/main/internal/query/trace.go) separates trace count/extent from paginated activities. | Retained volume, loaded detail, visible range, and display filters differ. Overall extent and coverage must remain meaningful without requiring every body; selection stays reachable and a filtered-out activity is not missing. No new latency SLA is implied. |
| S9. New projection commits arrive while the user reads an activity or while the two conversations are being read for comparison; later data can alter counts, time extent, and eligibility. | Architecture/interface — concurrent operation | Observed | R3/R7/R11; packet risk “concurrent-read consistency”; [projection API](https://github.com/kotokumu/agentmetry/blob/main/proto/agentmetry/v1/agentmetry.proto) streams committed change windows and supports session activity synchronization. | Retained data changes during an investigation. Reading must preserve the chosen activity and position; a result claiming one retained snapshot must not combine inconsistent evidence or leave coverage and eligibility detached from the data used. |
| S10. The retained projection available for an investigation lacks an evidence target or its parent, while received content may exist only in raw OTLP; all available projected records can nevertheless be read. | Architecture/interface — retention and projection coverage | Committed | R1/R6/R11; accepted scenarios “Evidence no longer available,” “Complete projection with unavailable content,” and “Context exists only in an unsupported span event”; packet fact that original protobuf and unsupported span events remain raw-retained. | Availability differs across retained raw data, canonical projections, topology, and the requested target. A complete projection read does not certify collection of the original execution; raw-only content remains outside canonical bodies, missing parents remain explicit, and unavailable exact evidence keeps its return path. |
| S11. A supported producer version adds or relocates context-bearing fields, or a separately approved mapping makes a previously unsupported received event interpretable. | Architecture/interface — provider contract evolution | Evidence-backed plausible | R9–R11 and the explicit separate-mapping constraint; [Codex snapshot](https://github.com/kotokumu/agentmetry/blob/main/docs/source-telemetry/codex.md) states that a complete stable event/span schema is not published; [Claude snapshot](https://github.com/kotokumu/agentmetry/blob/main/docs/source-telemetry/claude-code.md) documents version gates, beta traces, body references, and tool-output span events. No specific future mapping is scheduled. | The verified set of interpretable received fields changes. Existing raw ingestion must continue accepting unsupported attributes/events; investigation meaning can change only with the separately supported mapping and must preserve source, evidence strength, and availability. This scenario does not authorize new ingestion mappings. |
| S12. An MCP caller adds normalized comparison to an existing aggregate-analysis workflow and later explicitly requests activity content. | Architecture/interface — consumer access contract | Committed | R7/R8/R12; accepted scenario “Agent requests comparison without content”; [baseline MCP](https://github.com/kotokumu/agentmetry/blob/main/internal/transport/mcpserver/server.go) is read-only, caps activity pages at 100, and defaults `includeContent` to false. | The consumer uses more diagnostic capabilities without changing content authorization. Comparison responses remain body-free; explicit activity content reads retain existing limits and source-qualified identity, while old aggregate fields retain their meanings. |
| S13. A local Web profile contains saved conditions unsupported by the running client, or the client requests investigation functionality from a server that does not support it. | Architecture/interface — version compatibility | Committed | R5; accepted rule “Unsupported saved conditions SHALL be reported”; packet error cases “unsupported saved condition” and “unsupported server.” | Saved data and connected capabilities no longer match the current consumer. The mismatch must be visible rather than silently discarding conditions, reporting an unexecuted query as applied, or presenting unavailable functionality as an empty successful result. |
| S14. Local profile storage fails during saving, replacing, or deleting investigation conditions while ordinary investigation queries still work. | Architecture/interface — local persistence failure | Committed | R5; packet error case “local storage failure” and prohibition on marking a failed save successful; local application operation is required. | Persistence availability changes independently of telemetry reads. The affected operation must expose failure accurately and keep the actual saved/active conditions understandable; local saved state remains scoped to the Web profile. |
